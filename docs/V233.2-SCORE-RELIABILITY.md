# ATM Town v233.2 — Competition Score Reliability

This hotfix hardens the ATM Competition Engine against short mobile-network drops at the exact moment a run finishes.

## Client reliability

- A finished, session-verified result is written to a small local pending queue before submission.
- The active leaderboard session is not discarded until the API confirms the score.
- Pending results retry after the browser comes online, regains focus, becomes visible, and periodically while a pending result exists.
- Retry records are scoped to the signed-in ATM Town user and expire locally after 70 minutes.
- The game displays an explicit save state beside the game result: saving, verified/saved, queued for retry, or rejected/unverified.
- The queue is capped at 20 records and creates no traffic when it is empty.

## Server reliability

`api/leaderboards.js` now treats `session_id` as the idempotency key. The existing Supabase schema already enforces `arcade_scores.session_id` as unique.

If a browser loses the HTTP response after Supabase has already stored the score, a retry returns the existing verified score instead of rejecting the session or creating a duplicate. A duplicate insert race (`23505`) is also recovered by reading the score already attached to that session.

## No schema migration

No new Supabase table or column is required for v233.2. The existing v233 schema already has the unique `session_id` constraint needed for idempotent retries.
