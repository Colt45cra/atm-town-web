# ATM Town v234.2 — ATM Pay

## Goal

Make person-to-person XRPL payments feel like a normal consumer payment app. Players use ATM Town identities (`@handle`) instead of wallet addresses during normal Send, Request, and Activity flows.

v234.2 remains **XRPL Testnet only**. It does not enable Mainnet funds and does not replace Xaman.

## Player experience

ATM Pay adds:

- one-time unique `@handle` setup;
- recipient search by `@handle` or ATM Town display name;
- Send flow with recipient name/avatar, amount, optional note, review, then fresh wallet authorization;
- Request flow with incoming/outgoing requests;
- Activity showing validated payments and requests;
- no wallet-address entry, copy/paste, or suffix typing in normal payments;
- XRPL public address moved to Security → Advanced XRPL details.

## Settlement architecture

The normal UI uses ATM Town identity, but settlement remains a real XRPL Payment.

1. The authenticated browser asks the ATM Pay API to prepare a short-lived intent for a selected ATM Town user.
2. The server resolves the recipient user to their current ATM embedded Testnet wallet and stores the recipient, amount, route, address, and expiration in `atm_pay_intents`.
3. The browser receives the settlement address only as an internal field. It is never rendered in the normal payment UI.
4. xrpl.js autofills the Testnet transaction locally.
5. ATM Town adds one machine-only XRPL memo containing the unique ATM Pay intent ID, then hashes a canonical intent containing the ATM Pay intent ID, recipient user ID/handle, destination, amount, fee, sequence, expiration, and that exact memo. This prevents an older same-amount payment from being reused as proof of a new ATM Pay intent.
6. Immediately before signing, the browser asks the server to re-verify the intent and recipient route, then rechecks the live XRPL sequence/ledger.
7. Fresh passkey/recovery authorization decrypts the wallet only for `Wallet.sign()`.
8. After local signing, the server records only the transaction hash as `submitted`; the signed blob still never goes to ATM Town. This gives Activity a durable pending state if connectivity drops.
9. The browser submits the signed blob directly to XRPL Testnet with `submitAndWait()`.
10. The ATM Pay API independently looks up the transaction by hash on XRPL Testnet and records it only if the validated Payment matches the expected sender, destination, amount, and unique intent memo.

The signed transaction blob and plaintext seed/private key are not relayed through ATM Town's server.

## Database

Run `supabase/ATM-Town-v234.2.sql` before deployment.

It adds server-only RLS tables:

- `atm_pay_profiles` — unique public handles;
- `atm_pay_intents` — short-lived server-bound payment routes, durable submitted state, and validated activity records;
- `atm_pay_requests` — person-to-person requests, with a database guard preventing more than one active/completed payment per request.

No browser RLS policies are added.

## Vercel function budget

ATM Pay is routed through the existing `api/embedded-wallet.js` serverless function and implemented in `lib/atm-pay.js`. This intentionally keeps the existing 12-function Vercel Hobby deployment footprint rather than adding a 13th `api/*.js` function.

## Existing systems preserved

- v233.2 leaderboard score reliability/retry behavior;
- airborne Trade Beacon following local/remote jetpack players;
- Fuzzy collision-validated patrol route;
- existing Xaman wallet linking;
- Xaman vending and NFT trading remain explicit Mainnet paths;
- embedded ATM wallet remains explicit Testnet only;
- operation-scoped local wallet decryption and fresh authorization per signature.

## Not included yet

- Mainnet ATM Pay;
- Xaman as an ATM Pay sender/recipient route;
- QR payment links;
- nearby-player PAY action integration;
- ATM token issued-currency payments;
- handle changes/aliases;
- push notifications for requests.

Those can layer onto the same identity/intent architecture after the Testnet flow is live-tested.
