# ATM Town v234.1 — Embedded Wallet Security Hardening

## Scope

v234.1 hardens the existing optional ATM Embedded Wallet without enabling XRPL Mainnet. The embedded wallet remains XRPL Testnet-only. Existing Xaman/Mainnet account linking, vending, NFT trading, Trade Beacon behavior, Sky Run score reliability, bots, world streaming, voice, and unrelated gameplay remain separate.

## Security model after v234.1

### No persistent unlocked wallet session

The embedded wallet no longer keeps an XRPL wallet object or plaintext seed in module state after unlock. Preparing a payment uses only the public address. Every signing operation requires fresh wallet authorization.

For a signature:

1. The player reviews the prepared Testnet transaction.
2. The player confirms the final six characters of the full destination.
3. The player authorizes that operation with the wallet passkey or recovery key.
4. ATM Town rechecks the prepared intent and current validated-ledger account sequence.
5. The encrypted payload is decrypted only inside the operation-scoped signing callback.
6. The transaction is signed locally in the browser.
7. The vault-key byte buffer and decrypted payload byte buffer are cleared immediately after the operation.
8. Only the signed transaction blob is submitted directly from the browser to XRPL Testnet.

JavaScript strings and third-party library internals cannot be guaranteed to be physically zeroized by the browser garbage collector. This is why Mainnet remains disabled and why the operation-scoped lifetime is important.

### Transaction intent restrictions

The embedded wallet signs only a direct XRP `Payment` with this exact field allowlist:

- `TransactionType`
- `Account`
- `Destination`
- `Amount`
- `Fee`
- `Sequence`
- `LastLedgerSequence`

The wallet rejects unexpected fields, issued-currency Amount objects, paths, memos, destination tags, signer fields, and other transaction mutations. A SHA-256 digest of the canonical prepared intent is saved at preview time and recalculated before signing.

Existing safety limits remain:

- Testnet only
- maximum 10 XRP per test payment
- maximum accepted fee 0.01 XRP
- prepared-payment lifetime 60 seconds
- self-payment blocked

Immediately before signing, ATM Town checks the live validated account sequence and requires ledger-expiration headroom. A changed account sequence or stale preview forces the player to prepare the transaction again.

### Destination confirmation

The full destination address is shown in the review panel. The player must type the final six destination characters before authorization can proceed. This is an additional defense against accidental or UI-level destination substitution.

### Emergency seed export

Emergency Testnet seed export now requires fresh wallet authorization. The plaintext seed is copied directly to the secure clipboard path when available and is never inserted into the ATM Town DOM. The encrypted backup plus recovery key remains the preferred recovery mechanism.

## Server-side backup hardening

`api/embedded-wallet.js` now:

- accepts only the exact encrypted-backup v1 schema,
- validates canonical base64url values and expected cryptographic field sizes,
- rejects unsupported/extra fields,
- rejects secret/private-key-named fields as defense in depth,
- enforces Testnet and classic-address checks,
- prevents an existing ATM Town account's embedded-wallet public address from being silently replaced by a normal backup-save request,
- rejects unexpected backup identity changes,
- applies an 8-second XRPL Testnet RPC timeout,
- continues to store ciphertext/public metadata only.

No new Supabase migration is required for v234.1.

## Browser security headers

`vercel.json` is generated by `scripts/generate-security-headers.mjs`.

The deployment adds:

- Content Security Policy
- SHA-256 authorization for the five existing inline game script blocks
- no `unsafe-inline` or `unsafe-eval` in `script-src`
- `object-src 'none'`
- `base-uri 'none'`
- `frame-ancestors 'none'`
- restricted `connect-src`
- YouTube privacy-domain-only `frame-src`
- Referrer Policy
- MIME sniffing protection
- frame-deny protection
- Cross-Origin-Opener-Policy
- Permissions Policy
- HSTS

Runtime browser-library fallback was reduced from two CDN providers to one exact pinned package version provider. `unpkg.com` is no longer authorized in wallet/Supabase runtime configuration.

Whenever an inline script in `index.html` changes, run:

```bash
npm run security:headers
```

before validation/commit so the CSP hashes match the deployed file.

## Still NOT approved for Mainnet

v234.1 is a meaningful hardening milestone, not a Mainnet launch. The following remain release gates:

1. Self-host/vendor the audited browser wallet dependency instead of loading xrpl.js at runtime from a third-party CDN.
2. Prefer the same self-hosting treatment for other executable third-party browser dependencies that share the game page.
3. Establish reproducible dependency hashes/artifact provenance for wallet-capable releases.
4. Complete manual multi-device/passkey/recovery tests, including lost-device and restored-device scenarios.
5. Test CSP/voice/auth/Xaman behavior across the supported mobile/tablet browsers after deployment.
6. Perform an independent security review of the wallet/key lifecycle and transaction policy.
7. Add a separate, deliberate Mainnet feature flag and Mainnet-specific review. Do not convert Testnet configuration in place.

Until those gates are complete, the embedded wallet must remain Testnet-only. Existing Xaman Mainnet support remains the production path for real funds.
